# Million Minds Tech City Domain Consolidation and Organic Search Plan

## Executive decision

`www.millionmindstechcity.in` should become the single primary search domain. The two owned domains currently publish overlapping Million Minds Tech City, office-leasing, Ahmedabad, GCC, SEZ, amenities and news topics. Keeping both independently indexable asks Google to choose between two properties for the same entity and divides links, crawl activity, brand mentions and behavioral history.

The strongest ranking action is therefore a controlled site migration from `.com` to `.in`: prepare equivalent `.in` destinations, apply one-to-one permanent redirects, update every canonical/internal link/sitemap/profile, and submit a Change of Address in Search Console. Google recommends permanent server-side redirects for domain moves, says mappings should point to relevant destinations, and notes that permanent redirects do not inherently lose PageRank.[^5]

The `.in` codebase has a clean technical foundation. The live crawl found all 40 sitemap URLs returning 200, with unique titles/descriptions, one H1, self-referencing canonicals, Open Graph, Twitter cards and valid JSON-LD. The immediate blockers are domain infrastructure and consolidation, not adding unlimited new keyword pages.

Rank one cannot be guaranteed. Search results are generated by Google and vary by query, device, location, history, competitors and recrawl timing. This plan removes controllable limitations and concentrates the strongest available signals on `.in` without spam or deceptive claims.

## Scope and evidence

The audit crawled both owned sitemaps and then followed same-domain HTML links not listed in those sitemaps. It recorded status, redirect destination, content type, document size, title, description, canonical, robots directives, H1/H2, visible word count, social metadata, JSON-LD, image count, lazy loading and internal links.

- `.in`: 40 sitemap URLs; 40 HTML pages; no additional crawlable HTML discovered.
- `.com`: 36 sitemap URLs; 24 sitemap HTML pages; 12 sitemap PDFs; four additional internal URL variants; 28 HTML responses in the expanded dataset.
- Full machine-readable evidence: [`seo/live-crawl-audit.json`](seo/live-crawl-audit.json).
- Host, redirect and DNS evidence: [`seo/host-redirect-audit.json`](seo/host-redirect-audit.json).
- The live sites explicitly allow crawling and declare their respective sitemaps.[^1][^2][^3][^4]

This was a source and response audit, not a substitute for Search Console field data, server logs, CrUX/Lighthouse field data or a commercial backlink index. Those datasets are required to quantify current rankings, link equity and real Core Web Vitals.

## Critical findings

### P0 — `.in` apex DNS and HTTPS are broken

`https://www.millionmindstechcity.in/` returns 200 from Vercel with HSTS. However, the audit observed:

- `http://millionmindstechcity.in/` returning 200 with a 114-byte JavaScript lander pointing to `/lander`, instead of a server-side redirect.
- `https://millionmindstechcity.in/` failing TLS negotiation during the audit.
- Apex A records resolving simultaneously to `15.197.148.33`, `3.33.130.190` and `216.198.79.1`.
- `www.millionmindstechcity.in` correctly resolving by CNAME to Vercel.

The first two apex IPs are serving the lander path while the third points toward the intended hosting setup. This splits host behavior and can prevent the repository's configured host redirect from running.

Required action:

1. In the active DNS zone, remove the obsolete/parking apex A records after checking them against the Vercel Domains screen.
2. Configure the apex with the exact current Vercel A/ALIAS recommendation shown for this project; do not copy an old generic value blindly.
3. Add and verify both `millionmindstechcity.in` and `www.millionmindstechcity.in` in Vercel.
4. Issue/verify TLS for the apex.
5. Confirm all three variants return one-hop 301/308 responses to `https://www.millionmindstechcity.in/`:
   - `http://millionmindstechcity.in/`
   - `https://millionmindstechcity.in/`
   - `http://www.millionmindstechcity.in/`
6. Repeat the test for representative paths, not only the homepage.

Google recommends selecting one preferred URL and permanently redirecting alternate host/protocol versions to it.[^6]

### P0 — two owned domains split the entity

Both domains currently return indexable 200 pages for overlapping topics. Canonicals are internally correct but point to each domain's own URLs, so Google receives strong signals that both versions should remain indexed. Canonicals, sitemap inclusion and redirects can stack; redirects are the strongest listed canonicalization signal.[^7]

If `.in` is the required winner, leaving `.com` live with self-canonicals is strategically inconsistent. Cross-domain canonicals alone are weaker than a genuine migration because users, crawlers, internal links and many external links still land on `.com`.

Recommended decision: retire `.com` as a separate indexed website and migrate its useful content/assets to `.in`. Retain `.com` only as a permanent redirect host.

### P0 — official versus independent identity must be resolved

The `.in` site currently states that it is an independent leasing-assistance website and not the official developer site. Domain ownership alone does not establish permission to claim that PIKORUA Realty is Ganesh Housing or the official project publisher.

Before changing those disclosures or Organization schema, document one of these positions:

1. `.in` is the authorized official Million Minds Tech City website; provide the legal publisher/organization identity and authorization.
2. `.in` is owned by the same marketing group but operated independently; retain the current disclosure and distinguish the operator from the project/developer.

Incorrect identity claims create legal and trust risk and should not be used as a ranking tactic.

1. The live address/location page description was 170 characters at crawl time. It has now been shortened in the generator to 150 characters.
2. Seven utility/trust pages were below 300 words. These are About, Contact, Disclaimer, Editorial Policy, Privacy, Sources and Terms. Low word count is not automatically a problem for utility pages; do not inflate them with filler.

5. Current architectural images require rights and accuracy confirmation. Representational imagery must be labelled; actual project photography is preferable.
6. Search Console and analytics data were unavailable, so indexing quality, query cannibalization and lead quality cannot yet be proven.

## Domain migration design

### URL mapping

The complete working map is [`seo/domain-consolidation-map.csv`](seo/domain-consolidation-map.csv). It classifies each known `.com` URL as:

- `ready`: a relevant `.in` destination already exists.
- `review`: confirm that the destination visibly covers the original intent.
- `create_first`: publish an equivalent event/archive page before redirecting.
- `migrate_file`: copy the owned PDF to `.in`, validate it, then redirect.

Do not redirect every old URL to the `.in` homepage. Google warns that irrelevant mass-homepage redirects can be interpreted as soft 404s.[^5]

### Migration sequence

1. Fix `.in` apex DNS/TLS and deploy the current `.in` repository.
2. Confirm every proposed destination returns 200, is indexable and self-canonical.
3. Copy unique `.com` event pages and owned PDFs that still provide user value.
4. Update all `.in` links, schema, PDFs and contact references to preferred `.in` URLs.
5. Install one-to-one 301 rules on the `.com` Apache origin. A ready-only example is [`seo/com-to-in-redirects.htaccess.example`](seo/com-to-in-redirects.htaccess.example).
6. Remove `.com` URLs from its active sitemap after redirects launch; keep an old-URL monitoring list separately.
7. Submit the `.in` sitemap in Search Console.
8. Verify every `.com` and `.in` host variant in Search Console and submit Change of Address from `.com` to `.in`.[^5]
9. Update Ganesh Housing/project profiles, LinkedIn, campaigns, directories and important backlinks to `.in`.
10. Keep redirects for at least one year; preferably indefinitely. Monitor old-host traffic until it becomes negligible.[^5]

Do not combine the domain migration with a complete CMS redesign or mass URL rewrite. Move signals first using stable content and one-hop redirects, then improve templates after Google processes the change.

Each intent must have one primary owner. Supporting articles should link to that owner rather than competing with it using the same title, H1 and anchor language.

### Content that can outperform generic project marketing

1. **M One occupier due-diligence sheet:** carpet and chargeable area, floor height, lifts, HVAC, power, parking, floor loading, fit-out rules, certifications, possession and source date.
2. **Verified occupier tracker:** announced, leased, fit-out, operational and unverified must be separate states.
3. **SG Highway/GIFT corridor decision model:** commute catchments, airport access, talent pools, resilience, SEZ eligibility and total occupancy cost.
4. **Enterprise requirement calculator:** seats, usable area, meeting rooms, support space and expansion buffer.
5. **Document library:** owned brochure, policy and technical PDFs with HTML summaries, publication dates, file sizes and accessible titles.
6. **Original project media:** rights-cleared photos, captions, dates, locations and descriptive alt text.
7. **Named expertise:** author/reviewer credentials, correction mechanism and evidence standard.

The published project brochure describes the 65-acre integrated development and developer context.[^9] Recent milestones should remain source-labelled: the Press Information Bureau reported the May 2026 inauguration,[^10] and Incuspaze announced a 60,000 sq. ft. workspace with capacity for more than 1,200 seats.[^11] Current operational status and availability still require reconfirmation.

## On-page and entity standards

1. Titles should be unique, concise, entity-first and aligned with the visible H1. Google may build title links from the title, H1, prominent text, anchors, Open Graph title and WebSite structured data.[^12]
2. Descriptions should summarize the page honestly; avoid repeating every keyword.
3. Every indexable page should have one self-canonical, one clear H1 and useful internal links.
4. Use structured data only for facts visible on the page. Schema is an interpretation aid, not a ranking guarantee.
5. Keep project (`Place`), developer and site operator as distinct entities until official publishing authority is documented.
6. Give dated claims a source, verification date and status label.
7. Do not use `meta keywords`, hidden text, doorway pages, automated location permutations or fake reviews.

## Performance plan

1. Convert gallery assets to responsive AVIF/WebP while retaining fallbacks where needed.
2. Use `srcset` and `sizes`; serve near-display-size images instead of a single large file.
3. Keep the above-the-fold hero optimized for LCP and avoid fixed background effects on mobile.
4. Reserve image dimensions to prevent layout shift.
5. Delay non-essential scripts and audit the six-second lead popup's impact on interaction and conversion.
6. Measure mobile field data in Search Console after deployment. Lab scores alone are insufficient.

The `.com` crawl found seven HTML documents above 150 KB and several image-heavy pages. Those templates should not be copied directly to `.in`; migrate their content value, not their delivery cost.

## Authority consolidation

After redirects launch, update the links under direct control first:

1. Ganesh Housing project pages and corporate documents.
2. Million Minds Tech City LinkedIn and other official profiles.
3. Press boilerplates, media kits and event pages.
4. Advertising destinations and email signatures.
5. Business directories and broker profiles.
6. High-traffic backlinks identified in Search Console.

Then earn new links by publishing original data and tools. Purchased sitewide links, bulk directory blasts, spun guest posts and fake press are excluded because they create manual-action and reputation risk.

## Measurement framework

### Required Search Console properties

- Domain property for `millionmindstechcity.in`.
- URL-prefix properties for HTTP/HTTPS and www/non-www variants during diagnosis.
- Domain property for `millionmindstechcity.com` during migration.

### Weekly migration checks

- `.in` indexed pages and selected canonical.
- `.com` indexed pages and redirect discovery.
- Crawl errors, soft 404s and redirect chains.
- Branded queries split by `.com` and `.in` landing URL.
- Sitemap submitted versus indexed counts.
- Manual actions and security issues.

### 28-day business checks

- Non-branded impressions/clicks for office, M One, location, company and specification clusters.
- Qualified verified leads per organic session.
- Calls, emails and site-visit bookings attributed to landing page/query cluster.
- Conversion rate and abandonment before/after the six-second popup.
- New relevant referring domains and updated owned-profile links.

## Execution roadmap

### First 72 hours

1. Fix `.in` apex DNS and TLS.
2. Deploy the current repository.
3. Verify favicon, social image, six-second popup, canonical and sitemap on production.
4. Export both domains' Search Console performance, pages, links and sitemaps reports.
5. Confirm official/independent publisher status.

### Days 4–14

1. Review and approve the URL mapping.
2. Build missing event/document destinations on `.in`.
3. Migrate owned PDFs with accessible HTML summaries.
4. Test every redirect destination and preserve query parameters where appropriate.
5. Launch one-to-one `.com` 301 redirects during a lower-traffic window.
6. Submit Change of Address and the `.in` sitemap.

### Days 15–45

1. Monitor migration errors and correct irrelevant mappings immediately.
2. Update controlled external links and profiles.
3. Upgrade the M One, office-space, specification, location and companies pages with first-party detail.
4. Replace generic imagery with original project assets.
5. Add GA4 qualified-lead and site-visit events.

### Days 46–90

1. Publish the requirement calculator and document library.
2. Produce two to four source-led editorial assets based on real customer questions.
3. Run targeted digital PR and attribution outreach.
4. Consolidate any `.in` pages that Search Console shows competing for the same intent.
5. Compare 28-day periods; do not react to daily ranking volatility.

## Acceptance criteria

- Every `.in` host/protocol variant reaches `https://www.millionmindstechcity.in/` in one permanent hop.
- Every migrated `.com` URL reaches a relevant `.in` URL in one permanent hop.
- No `.com` self-canonical 200 HTML remains after full cutover.
- `.in` sitemap contains only 200, indexable, self-canonical preferred URLs.
- All priority `.in` pages pass metadata, H1, schema and link validation.
- Search Console reports `.in` as Google-selected canonical for priority queries.
- Qualified organic leads improve without a material rise in popup exits.
- Redirects stay operational for at least one year.
